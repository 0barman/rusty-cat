# Azure Blob direct upload/download guide

This guide explains how to use `rusty-cat` with Azure Blob Storage direct Shared Key authentication. Direct mode means the application process sends requests to Azure Blob Storage and signs each request with the storage account key.

Use direct mode only in trusted environments, such as backend services, internal tools, or controlled workers. A storage account key can grant broad access to the account, so it should not be embedded in public client applications.

The [`azure-direct`](../../test-app/README.md#provider-direct-场景) test-app
scenario exercises the official SDK direct provider with dedicated live-test
configuration and supports environment overrides. It is an internal test tool;
production applications must load their own credentials securely.

## Security model

Direct mode requires:

| Secret/value | Required for | Notes |
|---|---|---|
| `account_name` | Upload and download | Azure Storage account name. |
| `account_key` | Upload and download | Base64-encoded storage account key. Treat this as a high-value secret. |
| `container_name` | URL construction | Blob container name. |
| `blob_name` | URL construction | Blob path inside the container. |

`rusty-cat` does not persist account keys or tokens. It only uses the values you pass to `AzureBlobDirectUpload` and `AzureBlobDirectDownload` to sign requests in memory. Your application is responsible for secure loading, key rotation, least-privilege design, and ensuring secrets are never printed in logs.

For untrusted clients, prefer SAS URLs generated by a trusted backend instead of distributing account keys.

## Enable the feature

```toml
[dependencies]
rusty-cat = { version = "0.3.6", features = ["azure-blob-direct"] }
tokio = { version = "1", features = ["macros", "rt-multi-thread"] }
```

For an isolated live-test configuration, set these environment overrides in the
process that launches test-app:

- `RC_AZURE_ACCOUNT_NAME`
- `RC_AZURE_ACCOUNT_KEY`
- `RC_AZURE_CONTAINER`

Optional variables are `RC_AZURE_BLOB_PREFIX`, `RC_DIRECT_UPLOAD_SIZE`,
`RC_DIRECT_PART_SIZE`, and `RC_OUT_DIR`. Then run from the repository root:

```text
cargo run --manifest-path test-app/Cargo.toml -- azure-direct
```

The scenario uses `AzureBlobDirectUpload` and `AzureBlobDirectDownload` from
the SDK. The former hand-written Shared Key signer was not migrated, so
test-app has one direct implementation rather than two competing copies. Use a
least-privilege test credential and an isolated blob prefix.

## Upload flow

The upload side uses `AzureBlobDirectUpload`, which implements `BreakpointUpload`.

High-level process:

1. Build the final blob URL: `https://{account}.blob.core.windows.net/{container}/{blob_name}`.
2. Create `MeowClient` from `MeowConfig`.
3. Create `AzureBlobDirectUpload::new(account_name, account_key)`.
4. Build an upload task with `UploadPounceBuilder`.
5. Attach the protocol with `with_breakpoint_upload(Arc::new(upload_protocol))`.
6. Submit with `enqueue_and_wait(...)` (or manage terminal callbacks yourself).
7. Wait for the terminal result.
8. Close the client explicitly during shutdown.

The blob URL must identify the final blob that should be created. The provider plugin appends Azure query parameters such as `comp=block` and `comp=blocklist` internally when uploading and committing blocks.

```rust,no_run
use std::sync::Arc;

use rusty_cat::api::{MeowClient, MeowConfig, UploadPounceBuilder};
use rusty_cat::azure_blob_direct::AzureBlobDirectUpload;

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error + Send + Sync>> {
    let account_name = std::env::var("AZURE_STORAGE_ACCOUNT")?;
    let account_key = std::env::var("AZURE_STORAGE_KEY")?;
    let container = "test";
    let blob_name = "rusty-cat/demo.bin";
    let blob_url = format!("https://{account_name}.blob.core.windows.net/{container}/{blob_name}");

    let client = MeowClient::new(MeowConfig::builder().max_upload_concurrency(1).build()?);
    let upload_protocol = AzureBlobDirectUpload::new(account_name, account_key);

    let task = UploadPounceBuilder::new("demo.bin", "./demo.bin", 1024 * 1024)
        .with_url(blob_url)
        .with_breakpoint_upload(Arc::new(upload_protocol))
        .with_max_chunk_retries(3)
        .build()?;

    let outcome = client
        .enqueue_and_wait(
            task,
            |record| println!("upload progress={:.2}%", record.progress() * 100.0),
        )
        .await?;

    println!("upload {} complete: {:?}", outcome.task_id, outcome.payload);
    client.close().await?;
    Ok(())
}
```

### What the SDK does internally

`AzureBlobDirectUpload` performs the block blob workflow:

1. Validates Azure task constraints.
2. Signs requests with Shared Key using the account name and account key you provided.
3. Lists uncommitted blocks when resuming.
4. Uploads chunks with `Put Block`.
5. Commits the block list with `Put Block List` after all chunks are uploaded.
6. Checks Azure block count and block size limits before sending chunks.

## Download flow

The download side uses `AzureBlobDirectDownload`, which implements `BreakpointDownload`. The executor handles the resumable download workflow, while the provider plugin adds Azure Shared Key authorization headers to `HEAD` and range `GET` requests.

High-level process:

1. Build or receive the final blob URL.
2. Create `AzureBlobDirectDownload::new(account_name, account_key)`.
3. Build a `DownloadPounceBuilder` task with a local output path and chunk size.
4. Attach the provider plugin with `with_breakpoint_download(Arc::new(download_protocol))`.
5. Submit with `enqueue_and_wait(...)` and monitor `FileTransferRecord` updates.
6. Close the client explicitly when your application shuts down.

```rust,no_run
use std::sync::Arc;

use rusty_cat::api::{DownloadPounceBuilder, MeowClient, MeowConfig};
use rusty_cat::azure_blob_direct::AzureBlobDirectDownload;

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error + Send + Sync>> {
    let account_name = std::env::var("AZURE_STORAGE_ACCOUNT")?;
    let account_key = std::env::var("AZURE_STORAGE_KEY")?;
    let blob_url = "https://account.blob.core.windows.net/test/rusty-cat/demo.bin";

    let client = MeowClient::new(MeowConfig::default());
    let download_protocol = AzureBlobDirectDownload::new(account_name, account_key);

    let task = DownloadPounceBuilder::new("demo.bin", "./downloads/demo.bin", 1024 * 1024, blob_url)
        .with_breakpoint_download(Arc::new(download_protocol))
        .build();

    let outcome = client
        .enqueue_and_wait(
            task,
            |record| println!("download progress={:.2}%", record.progress() * 100.0),
        )
        .await?;

    println!("download {} complete", outcome.task_id);
    client.close().await?;
    Ok(())
}
```

## Restart recovery and database notes

The SDK has no built-in database. Persist your own business record with blob URL, local path, direction, chunk size, provider type, status, and credential reference. Rebuilt downloads reuse parts only from a generation-bound sidecar whose fresh strong ETag and local part digests validate; without that proof they download again from byte zero. Direct uploads can pause and resume in the same process, but the current public API cannot inject prior block-session progress into a new protocol instance after restart; reconcile or clean uncommitted blocks and start again.

Canceling a direct Azure upload runs the provider abort hook, which deletes the target blob. Confirm that this cleanup policy is appropriate for your application before exposing cancel to users.

For direct Azure mode, avoid storing raw account keys in your transfer table. Store a credential reference or load the key from your secret manager at runtime. This keeps transfer persistence separate from credential storage and reduces the blast radius of a database leak. See the [restart capability matrix](resume-after-restart.md).

## Troubleshooting

| Symptom | Common cause | Fix |
|---|---|---|
| `403` authentication failure | Wrong account key, malformed URL, bad clock, or Shared Key canonicalization mismatch. | Verify account name/key, blob URL, and local clock. |
| Block size error | Chunk size exceeds Azure block limits. | Use a smaller `chunk_size`. |
| Too many blocks | File is too large for the chosen chunk size. | Increase `chunk_size` while staying under Azure per-block limits. |
| Blob not visible after upload | Commit block list failed. | Check completion callback status and server response body in errors/logs. |
