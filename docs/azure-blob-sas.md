# Azure Blob SAS upload/download guide

This guide explains how to use `rusty-cat` with Azure Blob SAS URLs. SAS mode means a trusted backend keeps the Azure credentials and creates short-lived SAS URLs. The client executes `Put Block`, `Put Block List`, and range `GET` requests, and may also send `HEAD` during download preparation unless the object size is provided in the download plan.

SAS mode is the preferred Azure integration for untrusted clients. The storage account key stays on your backend, while the client receives a scoped URL with limited permissions and a limited lifetime.

Runnable test coverage lives in [`test-app`](../../test-app/README.md): the
`loonadm` path consumes backend-issued upload URLs, while
[`download::oss_azure`](../../test-app/src/download/oss_azure.rs) exercises a
read-only Azure SAS download.

## Security model

The SDK does not generate Shared Key signatures, does not request Microsoft Entra ID tokens, and does not receive or persist account keys. Your backend should:

1. Authenticate the user.
2. Decide the storage account, container, blob name, file size, and chunk size.
3. Generate a SAS URL with enough permissions for the requested operation.
4. Return temporary URLs and metadata to the client.

For upload, the SAS token generally needs write (`w`) permission, and create (`c`) permission when creating a new blob. For download, the SAS token needs read (`r`) permission and must allow range requests. If the download plan does not provide a known blob size, the URL used for preparation must also permit `HEAD`. Keep SAS lifetimes as short as your transfer requirements allow, and issue fresh SAS URLs when a transfer is resumed after a long pause or process restart.

## Enable the feature

```toml
[dependencies]
rusty-cat = { version = "0.3.6", features = ["azure-blob-sas"] }
tokio = { version = "1", features = ["macros", "rt-multi-thread"] }
```

Run the backend-issued presigned/SAS flow from the repository root:

```text
cargo run --manifest-path test-app/Cargo.toml -- loonadm
```

The upload URLs come from the backend multipart-init response. The fixed
read-only validation URL is `AZURE_SAS_URL` in
[`test-app/src/config.rs`](../../test-app/src/config.rs). To validate another
SAS download without running the backend flow, set `RC_DIRECT_URL` and run the
`direct-download` test-app scenario.

```text
cargo run --manifest-path test-app/Cargo.toml -- direct-download
```

## Upload flow

The upload side uses the provider-neutral `PresignedMultipartUpload` abstraction, mapped to Azure Block Blob `Put Block` and `Put Block List` operations through helpers from `rusty_cat::azure_blob_sas`.

High-level process:

1. Your backend returns a blob SAS URL.
2. The client creates one `Put Block` URL per chunk with `azure::put_block_from_blob_url(...)`.
3. The client creates block IDs with `azure::block_id_by_index(...)`.
4. The client creates a `Put Block List` completion request with `azure::put_block_list_request(...)`.
5. The client creates `PresignedMultipartUploadPlan` and attaches it to `UploadPounceBuilder`.
6. Submit with `enqueue_and_wait(...)` (or manage terminal callbacks yourself).
7. Let the configured completion request commit the block list after all chunks have been uploaded.

The block IDs generated by `azure::block_id_by_index(...)` must be the same IDs used in the completion request. If the list is incomplete or ordered incorrectly, Azure may create a blob with missing data or reject the commit.

```rust,no_run
use std::sync::Arc;

use rusty_cat::api::{
    MeowClient, MeowConfig, PresignedMultipartUpload, PresignedMultipartUploadPlan,
    UploadPounceBuilder,
};
use rusty_cat::azure_blob_sas as azure;

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error + Send + Sync>> {
    let blob_sas_url = "https://account.blob.core.windows.net/container/blob.bin?sv=...&sig=...";
    let chunk_size = 1024 * 1024;
    let total_size = 5 * chunk_size;

    let parts = (0..5)
        .map(|i| azure::put_block_from_blob_url(blob_sas_url, i, i as u64 * chunk_size, chunk_size))
        .collect::<Result<Vec<_>, _>>()?;

    let block_ids = (0..5).map(azure::block_id_by_index).collect::<Vec<_>>();
    let block_id_refs = block_ids.iter().map(String::as_str).collect::<Vec<_>>();
    let complete_request = azure::put_block_list_request(blob_sas_url, block_id_refs)?;

    let upload_protocol = PresignedMultipartUpload::new(
        PresignedMultipartUploadPlan::new(total_size, chunk_size, parts)
            .with_complete_request(complete_request),
    );

    let client = MeowClient::new(MeowConfig::default());
    let task = UploadPounceBuilder::new("azure-sas.bin", "./azure-sas.bin", chunk_size)
        .with_url(blob_sas_url)
        .with_breakpoint_upload(Arc::new(upload_protocol))
        .build()?;

    let outcome = client
        .enqueue_and_wait(
            task,
            |record| println!("upload progress={:.2}%", record.progress() * 100.0),
        )
        .await?;

    println!("upload {} complete: {:?}", outcome.task_id, outcome.payload);
    client.close().await?;
    Ok(())
}
```

### What the SDK does internally

The presigned upload abstraction sends each chunk to the generated `Put Block` URL. After all chunks succeed, it sends the completion request generated by `put_block_list_request(...)`, which commits the block list and makes the blob visible. Until the block list is committed, uploaded blocks may exist as uncommitted blocks and the final blob may not be readable.

## Download flow

The download side uses `PresignedRangeDownload` and `PresignedRangeDownloadPlan`. The plan contains the SAS URL used for range requests and can optionally include the known blob size.

High-level process:

1. Your backend returns a read-capable SAS URL.
2. Create `PresignedRangeDownloadPlan::new(download_sas_url)`.
3. If the backend knows the blob size, call `with_total_size(size)` to avoid a `HEAD` request.
4. Attach `PresignedRangeDownload` to `DownloadPounceBuilder`.
5. Submit with `enqueue_and_wait(...)` and await the terminal result.
6. If the SAS URL expires during a long download, request a fresh SAS URL from your backend and retry according to your application policy.

`with_total_size` skips HEAD. It therefore cannot authenticate or reuse an old
`.rcdl` checkpoint; existing local bytes are fetched again from byte zero. For
cross-process resume, provide a HEAD-capable metadata URL that returns a strong
ETag. Whether serial or parallel, a run needing multiple ranges must receive one
stable strong ETag on every 206 response; a one-range run may omit it only when
HEAD did not prepare a validator.

```rust,no_run
use std::sync::Arc;

use rusty_cat::api::{
    DownloadPounceBuilder, MeowClient, MeowConfig, PresignedRangeDownload,
    PresignedRangeDownloadPlan,
};

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error + Send + Sync>> {
    let download_sas_url = "https://account.blob.core.windows.net/container/blob.bin?sv=...&sig=...";
    let total_size = 5 * 1024 * 1024;

    let download_protocol = PresignedRangeDownload::new(
        PresignedRangeDownloadPlan::new(download_sas_url).with_total_size(total_size),
    );

    let client = MeowClient::new(MeowConfig::default());
    let task = DownloadPounceBuilder::new(
        "azure-sas.bin",
        "./downloads/azure-sas.bin",
        1024 * 1024,
        download_sas_url,
    )
    .with_breakpoint_download(Arc::new(download_protocol))
    .build();

    let outcome = client
        .enqueue_and_wait(
            task,
            |record| println!("download progress={:.2}%", record.progress() * 100.0),
        )
        .await?;

    println!("download {} complete", outcome.task_id);
    client.close().await?;
    Ok(())
}
```

## Backend contract checklist

For upload, return blob SAS URL, total file size, chunk size, SAS expiration timestamp, and optional server-side business upload ID. Your backend should be able to create a new SAS URL for the same blob if the client needs to resume later.

For download, return a read-capable SAS URL, optional known blob size, SAS expiration timestamp, and optional extra headers. Returning the known blob size lets the client skip `HEAD`. If `with_total_size(...)` is not used, the URL used for preparation must permit `HEAD`.

## Resuming after a restart

Because `rusty-cat` stores no state across restarts, resuming a SAS block upload after a kill/crash means rebuilding the task yourself. Persist your server-side business upload id and the `PresignedUploadedPart` records as blocks complete (read them from a clone of the upload protocol via `uploaded_parts().await`). On restart, request fresh SAS URLs from your backend, reconcile remote blocks, rebuild the plan, and re-inject confirmed parts with `with_resumed_parts(...)` before enqueue. The SDK resumes past the verified contiguous prefix and re-sends the rest.

See [Presigned multipart lifecycle](presigned-lifecycle.md) and the [restart capability matrix](resume-after-restart.md).

## Troubleshooting

| Symptom | Common cause | Fix |
|---|---|---|
| `403` from Azure | SAS expired, missing permission, or URL modified incorrectly. | Regenerate SAS and verify permissions. |
| Upload chunks succeed but blob is missing | `Put Block List` completion request failed or was not configured. | Use `put_block_list_request(...)` and inspect completion errors. |
| Download fails at prepare | SAS URL does not allow `HEAD`. | Use `with_total_size(...)` if your backend knows the size. |
| Range request fails | SAS lacks read permission or blob does not exist. | Verify SAS permissions and blob path. |
